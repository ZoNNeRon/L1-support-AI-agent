# Обогащение базы знаний (самообучение)

Шаг, который живой специалист «должен, но на практике часто забывает». Именно он замыкает контур: эскалация → решение → новая статья → следующая такая заявка закрывается сама, без второй линии.

Без этого шага агент остаётся дорогим маршрутизатором: тот же инцидент через неделю снова уйдёт инженеру.

## Когда запускается

- Вторая линия ответила по заявке - `get_l2_response(ticket_id)` вернул решение.
- Разработка закрыла Issue - `resolve_issue` вернул описание решения.
- Плановый разбор пробелов - `kb_coverage_gaps()` показывает темы, по которым поиск регулярно даёт низкую уверенность. Это очередь на написание статей.

## Шаг 1. Получить решение и его источник

`get_l2_response(ticket_id)` вернёт `root_cause` (первопричину) и `resolution` (что сделали). Оба поля важны: причина объясняет, когда инструкция применима, решение - что делать.

Ответа ещё нет (`pending: true`) - статью не пиши. Инструкция, собранная из догадок, хуже, чем её отсутствие: она выглядит авторитетно и уводит следующего специалиста не туда.

## Шаг 2. Проверить, что статьи ещё нет

`kb_search` по симптому из исходной заявки. Уже есть подходящая статья - значит проблема была не в отсутствии инструкции, а в том, что поиск её не нашёл. Тогда новая статья не нужна, полезнее расширить ключевые слова существующей, и это отдельная задача для человека.

## Шаг 3. Написать статью от симптома, а не от причины

Ключевой момент. Следующий пользователь придёт с теми же словами, что и первый: «портал не открывается». Он не знает и не может знать про истёкший сертификат.

Поэтому:

- **заголовок** - по симптому, как его видит пользователь;
- **`symptoms`** - формулировки из исходной заявки, включая разговорные;
- **`keywords`** - слова, которыми люди описывают эту проблему, а не термины из ответа инженера. Поиск работает по совпадению слов: статья с ключевым словом «reverse-proxy» не найдётся по запросу «не открывается портал»;
- **`solution_steps`** - шаги из решения, в порядке выполнения.

Разделяй адресатов. Шаги, требующие прав второй линии, помечай явно - чтобы следующий специалист L1 понимал, где заканчиваются его полномочия и начинается эскалация.

## Шаг 4. Создать

```
kb_create_article(
    title="заголовок по симптому",
    category="одна из пяти категорий справочника",
    keywords=["слова", "которыми", "опишет", "пользователь"],
    symptoms="как проблема выглядит со стороны заявителя",
    solution_steps=["шаг 1", "шаг 2"],
    source_ticket_id="13",
    source_reference="ответ L2 @net_admin_ivan по тикету 13",
)
```

`source_reference` обязателен - без него инструмент откажет. Это защита от главного риска самообучения: агент не должен пополнять базу знаний собственными предположениями. У каждой статьи есть автор решения, и он не агент.

Статья создаётся в статусе `draft` и сразу доступна поиску, но помечена как непроверенная. Публикует её человек. Обойти это нельзя, да и не нужно: непроверенная инструкция в базе знаний опаснее пробела в ней.

## Шаг 5. Закрыть исходную заявку

Вернись к тикету, с которого всё началось: у пользователя теперь есть решение. Ответь ему через `l1-resolve-kb`, сославшись на новую статью, и закрой заявку.

## Проверка результата

Прогони `kb_search` по формулировке из исходной заявки. Новая статья должна оказаться в выдаче - если её там нет, ключевые слова подобраны от причины, а не от симптома, и всю работу придётся считать несделанной.
