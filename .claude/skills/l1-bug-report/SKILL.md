# Баг-репорт в разработку (Сценарий В)

Пользователь нашёл дефект программы: ошибка 500, белый экран, отчёт считает неправильно, приложение вылетает по таймауту. Первая линия это не чинит - задача в том, чтобы разработка получила воспроизводимую задачу, а не пересказ жалобы.

## Шаг 1. Проверить дубликаты - до всего остального

`find_duplicate_issue(summary)` - вызывать **до** `create_bug_report`.

Одно и то же описание в очереди встречается по несколько раз: пять человек столкнулись с одной ошибкой - пять заявок. Пять одинаковых Issue в репозитории - это ровно та рутина, которую агент должен убирать, а не создавать.

Дубликат найден - переходи к шагу 5.

## Шаг 2. Восстановить шаги воспроизведения

Пользователи описывают результат, а не путь к нему: «при нажатии на Сохранить появляется белый экран». Шаги нужно восстановить из описания, оставаясь в границах фактов.

Правило: **каждый шаг должен следовать из текста заявки**. Достраивать очевидные промежуточные действия («открыть раздел», «заполнить форму») можно, выдумывать конкретику (версии браузера, названия кнопок, которых нет в описании) - нельзя. Разработчик, который не сможет воспроизвести баг по твоим шагам, потратит время впустую и вернёт задачу.

Чего в описании не хватает - не додумывай, а укажи в техническом контексте, что этих данных заявитель не сообщил.

## Шаг 3. Разделить ожидаемое и фактическое

- `expected` - что должно было произойти по логике действия («форма сохраняется, появляется подтверждение»);
- `actual` - что произошло на самом деле, словами из заявки («открывается пустой белый экран, данные не сохранены»).

Это не бюрократия: разница между этими двумя полями и есть формулировка бага.

## Шаг 4. Завести Issue

```
create_bug_report(
    ticket_id,
    title="короткий заголовок по сути дефекта",
    steps_to_reproduce=["...", "..."],
    expected="...",
    actual="...",
    technical_context="что известно об окружении, частоте, охвате",
    logs="", # только если пользователь их приложил
    severity="Критический|Высокий|Средний|Низкий",
)
```

`title` - по дефекту, а не по эмоции. Плохо: «Не работает сохранение!!!». Хорошо: «Белый экран при сохранении формы в модуле заявок».

`technical_context` - место для всего, что поможет разработчику сузить поиск: сколько пользователей затронуто, воспроизводится ли стабильно, когда началось, связано ли с недавним обновлением. Если чего-то не знаешь - так и напиши.

`logs` оставляй пустым, когда логов нет. Инструмент сам пометит, что они запрошены через тикет. Не сочиняй правдоподобный текст ошибки - выдуманный стек-трейс хуже его отсутствия.

`severity` согласуй с приоритетом заявки, посчитанным при триаже.

Инструмент сам подберёт репозиторий и метки по категории, свяжет Issue с заявкой и переведёт её в работу.

## Шаг 5. Если дубликат найден

`link_ticket_to_issue(ticket_id, issue_number)` - привязать заявку к существующему Issue.

Не создавай второй Issue «на всякий случай». Привязка полезнее: она показывает разработке реальный масштаб проблемы - сколько пользователей пришло с одним и тем же дефектом.

## Шаг 6. Ответить пользователю

Человек написал в поддержку и должен получить ответ, а не тишину. Сообщи, что проблема подтверждена как дефект и передана в разработку.

```
reply_to_ticket(
    ticket_id,
    message="текст уведомления",
    reply_kind="status_update",
)
```

`reply_kind="status_update"` - именно для этого случая. Ссылка на статью базы знаний здесь не нужна и не требуется: ты сообщаешь о ходе работы, а не даёшь инструкцию. Требование цитаты действует только для `reply_kind="solution"`.

**Не подставляй произвольную статью, чтобы «пройти проверку».** Если тянет процитировать что-то отдалённо похожее - значит, вид ответа выбран неверно.

Что написать: дефект подтверждён, передан в разработку, чего ждать дальше. Если для воспроизведения не хватает данных - задай вопросы здесь же, одним списком.

Заявку такой ответ не закрывает: решения у пользователя пока нет. Она остаётся в работе до ответа разработки.

Обходной путь стоит упомянуть, только если он есть в базе знаний, - тогда ответ становится `solution`, статья цитируется законно и попадает в `kb_article_ids`.

## Что дальше

Когда разработка закроет Issue с описанием решения (`resolve_issue`), оформи его статьёй - процедура `l1-kb-enrich`.
